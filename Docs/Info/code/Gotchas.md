# UnrealScript Gotchas

This document is for programmers experienced in languages like C++ or Java to uncover non-obvious caveats in UnrealScript and explain why writing "clean code" from a C++ perspective may lead to poor UnrealScript performance.

Short answers to "which is faster?" and "does the engine do X for me?" questions that come up while
writing KF1 mods. Each entry describes how the UE2.5 script virtual machine actually behaves, not how
a modern compiler would.

UnrealScript is compiled to **bytecode** and run by an **interpreter**. Every expression is a chain
of small opcodes, each dispatched through a function table. There is no optimizer, no JIT and no
inlining. Keep that picture in mind: the cost of a line is roughly the number of opcodes it compiles
to, plus whatever work the opcodes themselves do.

## Parse Strings Like A Noob
Seriously, your C/C++ background shoots you in the foot when you try to apply that knowledge to UScript. Unreal's `string` is not your typical `const char *` or `std:string`.

Let's say you need to parse CSV data and yield each field to `process()`. Which route would you take: `processCSV_Pro` or `processCSV_Noob`?
```js
function processCSV_Pro(string data) {
    local int i, pos;

    if (data == "")
        return;

    pos = InStr(data, ",");
    while (pos != -1) {
        process(i++, Left(data, pos));
        data = Mid(data, pos + 1);
        pos = InStr(data, ",");
    }
    process(i, data);
}

function processCSV_Noob(string data) {
    local int i, pos;
    local array<string> fields;

    Split(data, ",", fields);
    for (i = 0; i < fields.length; ++i) {
        process(i, fields[i]);
    }
}
```
An experienced C++ developer picks `processCSV_Pro()` without a thought: one memory allocation for a temporary string vs. allocating a dynamic array + per-field `malloc()`. Then they wonder why their UnrealScript is so slow.

`processCSV_Noob()` works faster by a margin! The game doesn't care about memory allocation - it allocates much more just for farting (literally - check `ScrnHumanPawn.Fart`). However, in the first case, there are significantly more function and operator calls, each of them adding substancial overhead. Moreover, there are hidden memory allocations in the "Pro" version where you'd never expect. Let's count all the gotchas in `processCSV_Pro`:
1. `data == ""`, meant for early-return optimization, in reality is a native function call: `operator==(data, "")`. All UScript functions (native and non-native) accept arguments **by value** (even when marked `out`, but that's a different story). Hence, UE **copies** data and an empty string to check if boths are equal. You wanted an optimization, but you shot yourself in the foot.
2. `InStr` also copies `data` - for the second time. The only hope is that UE reuses the same buffer as in #1 - that would save you for `malloc()`, but `memcpy()` is called in any case.
3. `pos != -1` is another native function: `operator !=(pos, -1)`. Luckily, both arguments are integers, so no memory allocations here.
4. `process(i++, Left(data, pos));` - copies `data` to pass it into `Left`, then copies the return of the `Left()` (a copy of a temporary string) to pass it to process. **Two string copies** instead of one.
5. `i++` is also a native function call: `postoperator int  ++ ( out int A )`.
6. `Mid()` produces **3 string copies**: a) copy `data` into Mid's argument; b) copy Mid's result into a temporary string; c) copy a temporary string back to `data`. Let's not blame Timmy too harsh - UT2004 was written way before C++11, so no move semantics existed yet. However, I'd still expect two copies instead of three.
7. `InStr` - yet another string copy.
8. Repeat #3-7 for every comma in the string: 6x string copies per cycle.
9. Yet another string copy in the last `process` - but that's expected.

Now, let's compare it with `processCSV_Noob()`:
1. `Split` - one `data` copy, followed by multiple relatively fast memory allocations in C++, and final `memcpy()` back into `fields`.
2. Two string copies per cycle: `operator[]` + copy into `process`.

`processCSV_Noob()` saves 4 string copies per every comma in the text - and those 4 are the longest ones, as they apply to the rest of the string.


## Operators are native function calls

In C++ a comparison is nearly free and a function call is what costs. In UnrealScript that intuition
is wrong: an operator **is** a function. `Object.uc` declares them side by side:

```unrealscript
native(122) static final operator(24) bool == (string A, string B);
native(126) static final function int      InStr(coerce string S, coerce string t);
```

Both compile to the same kind of opcode and are dispatched the same way: a native numbered below 256
is a one-byte opcode, a higher one is two bytes. "Operator" is only parsing syntax — `a == b` and
`InStr(a, b)` go through exactly the same machinery.

What a native costs is dominated not by its work but by **reading its arguments** — see the next
section. So a "cheap" guard in front of a native often costs as much as the call it tries to avoid:

```unrealscript
// slower: for a non-empty s this runs two natives and copies s twice
if (s == "")
    pos = -1;
else
    pos = InStr(s, ",");

// faster: InStr on an empty string already returns -1
pos = InStr(s, ",");
```

For an empty `s` the two are a wash; for a non-empty `s` the guard is pure overhead. Guards pay off
only in front of **script** (non-native) function calls, and only when the guard itself uses cheap
operands — an `int`, a `bool`, `!= none` — not strings.

## Arguments are always passed by value

UnrealScript has no references. Every argument, to a native or a script function, is evaluated
**into a fresh buffer** owned by the callee. For an `int` or an object reference that is 4 bytes. For
a `string` it is a new string: a heap allocation plus a copy of the characters (empty strings are
cheap — there is nothing to allocate). For a dynamic array it is a copy of the whole array.

So `if (s1 == s2)` copies both `s1` and `s2` just to compare them, and frees both copies afterwards.

Why can a native not simply look at the caller's variable? Because an argument can be any expression:
a variable, but also `a $ b` or another function's result, which have no address. The interpreter
treats them all alike — evaluate the expression, write the value into the destination — and only
afterwards reveals which variable, if any, it came from.

### `out` does not avoid the copy

The popular belief is that `out` passes by reference. It does not:

- **Native function, `out` parameter:** the value is still copied in first, exactly like a normal
  parameter. Only then does the native switch to the caller's variable so it can write back.
- **Script function, `out` parameter:** the value is copied into the function's frame, the function
  works on that copy, and on return the copy is written **back** over the caller's variable —
  including after an early `return`. That is **two** full copies instead of one.

For arrays this is expensive. Passing an `array<int>` as `out` reallocates and copies the array twice;
an `array<string>` copies every element string individually, twice, and on the way back first
destroys and rebuilds all the caller's strings — even though nothing changed.

```unrealscript
// "out for performance" — actually twice as slow as without out
static final function int BinarySearch(out array<int> arr, int val)

// read-only parameter: one copy
static final function int BinarySearch(array<int> arr, int val)
```

Two side effects of the copy-back are worth knowing:

- **It writes to whatever you passed**, even when the function never assigned the parameter. Pass
  `default.SomeArray` and every call rewrites the class default.
- **It is copy-in/copy-out, not aliasing.** If the function (or something it calls) modifies the
  original variable directly during the call, that change is overwritten when the parameter is copied
  back.

Inside the function, reading `arr[i]` or `arr.Length` does **not** copy the array — the cost is
purely at the call boundary. Rules of thumb:

- Use `out` only when the function really writes the parameter back.
- A read-only array parameter should be a plain parameter: one copy instead of two.
- The only way to avoid the copy entirely is not to pass the array: write the loop at the call site,
  or reach the array through an object reference (`SomeObj.Arr[i]` reads in place).

## Count the string copies

Built-in string functions — `Left`, `Right`, `Mid`, `Caps`, `Locs`, `$` and the rest — follow one
pattern: copy every string argument, build the result as a temporary string, then copy the temporary
into the destination. There is no move semantics (the engine predates C++11).

`str = Left(str, 5)` therefore makes **three** string copies:

| # | Copy | Size |
|---|---|---|
| 1 | `str` into `Left`'s argument | the **whole** `str` |
| 2 | the result built as a temporary | 5 characters |
| 3 | the temporary into `str` | 5 characters |

There is no fourth copy: an assignment hands the variable itself to the function as its return
destination. The same happens when the result is passed straight into another function's parameter.
The first copy is also what keeps `str = Left(str, 5)` safe — `Left` reads its own copy while it
writes into `str`.

Chains multiply: `s = Left(s, p) $ Mid(s, p + 4)` copies all of `s` twice, each piece twice more, then
concatenates and copies the result. In code that runs every tick, or per character of a long string,
prefer fewer, bigger native operations, and compare `name`s instead of `string`s where you can —
comparing two names is an integer comparison with no allocation.

## Local variables are free

A `local` declaration compiles to **no opcode at all**. On every call the engine reserves one stack
frame for all parameters and locals and zeroes it in a single pass — that holds for events the engine
calls, such as `Tick`, as well as for ordinary script calls. An extra `local int`, `float`, `bool`,
`name`, object reference or plain struct (`vector`, `rotator`) only makes that one zeroing a few bytes
longer. That is also why every local starts at `0` / `none` / `""` without explicit initialization.

The exception is a local that needs destruction — a `string`, a dynamic array, a delegate, or a struct
containing one of those. Each such local is destroyed on **every** call, whether or not it was used.
Still cheap, but it is the only kind of local with a real per-call cost.

So do **not** move a rarely executed block out of a hot function just to "save" its locals:

```unrealscript
function Tick(float dt)
{
    local Controller C;  // used only every 10th tick — keep it here
    ...
}
```

Moving the block into a separate function saves zeroing 4 bytes on nine ticks out of ten, and pays for
a whole script call on the tenth — frame setup, argument evaluation, the replication and state checks
listed under *What every script call costs* below. That is orders of magnitude more. Split functions
for readability, not for speed.

## Typecast vs. `IsA()`

Both of these test whether `Weapon` is a `KFMeleeGun`:

```unrealscript
if (KFMeleeGun(Weapon) != none) { ... }
if (Weapon.IsA('KFMeleeGun')) { ... }
```

Leaving aside the usual differences (the cast is `none`-safe; `IsA()` takes a `name`, so it accepts
typos but does not need the other package linked), **they cost the same**.

| | Typecast `!= none` | `IsA()` |
|---|---|---|
| Opcodes executed | ~5: the `!=` operator, the cast, the variable read, `none`, end of parameters | ~5: the `Weapon.` context switch, the variable read, the two-byte native call (`IsA` is `native(303)`), the name constant, end of parameters |
| Class hierarchy walk | walks the object's class up to `Object`, comparing class references | walks the same chain, comparing class **names** |
| Destroyed-actor checks | 2 (`!=` treats an actor with `bDeleteMe` as `none`, on both operands) | 1 (the `Weapon.` context) |

- **`IsA()` does not compare strings.** A `name` is stored as an index into the global name table,
  so comparing two names is an integer comparison. The `'KFMeleeGun'` literal is resolved once, when
  the package loads.
- **The hierarchy walk has the same length in both cases.** A failed test — the common case — walks
  all the way up to `Object`, about eight levels for a `KFWeapon` subclass. `IsA()` reads one extra
  field per level (the class name), the cast does one extra destroyed-actor check. The two roughly
  cancel out, and either difference is far below measurement noise.

**Where the cast really wins:** when you use the result afterwards.

```unrealscript
MeleeGun = KFMeleeGun(Weapon);
if (MeleeGun != none) {
    MeleeGun.Foo();
}
```

With `IsA()` you still need `KFMeleeGun(Weapon).Foo()` afterwards — a second hierarchy walk and a few
more opcodes. So pick between the two on the grounds of package coupling and typo-safety, not speed.

## `final` and `static` functions are never inlined

Coming from C++ it is tempting to write small helpers as `static final function` and assume the
compiler folds them into the caller. **It does not.** Every call to a script function, whatever its
specifiers, is a real call with its own stack frame.

### What `final` buys

- A **non-`final`** call is stored in the bytecode by function **name**. At run time the engine looks
  the name up in the object's current state and class to find the override to run.
- A **`final`** call is stored as a direct reference to the function, so that lookup is skipped.

That is all. `final` saves the lookup, not the call.

### What `static` buys

Nothing, performance-wise. `static` only means the function has no instance to work on; the compiler
enforces that you do not touch instance members. The *call site* decides the cost:

- `Foo()` called from within the same class hierarchy — the same as any other `final` call.
- `class'X'.static.Foo()` — adds a class-context opcode that evaluates the class and fetches its
  default object before the call.
- `SomeObject.Foo()` — adds an object-context opcode, including the destroyed-actor check.

### What every script call costs

Regardless of `final` or `static`, calling a function written in UnrealScript:

1. Reserves a stack frame big enough for all the parameters **and locals**, and zeroes it.
2. Evaluates each argument into that frame, one parameter at a time, and records `out` parameters.
3. Runs the replication check (is this a `Server*` / `Client*` call that must be sent over the
   network?) — even for a `static` function.
4. Checks the `singular` flag and whether the function is enabled in the current state (probe check).
5. Interprets the body opcode by opcode, up to its `return`.
6. Copies `out` parameters back, and destroys locals that need it (`string`s, dynamic arrays).

Native functions (declared `native` in UnrealScript) skip most of this: their C++ implementation reads
the arguments directly.

### In practice

A helper like

```unrealscript
static final function bool IsMelee(Weapon W)
{
    return KFMeleeGun(W) != none;
}
```

costs **several times** the typecast it wraps: frame setup and zeroing, the replication and state
checks, plus extra opcodes for the call, the parameter read and the return.

- For code that runs once per event (a kill, a pickup, a menu click) this is irrelevant. Write the
  helper — readability wins.
- In a **hot loop** — every tick, or over `Level.ControllerList` / `DynamicActors()` with dozens of
  zeds — writing a trivial expression inline instead of calling a helper is measurably cheaper.

UnrealScript has no `inline` keyword and no macros, so there is no way to get the helper's readability
without paying for the call.
