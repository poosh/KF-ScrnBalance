# Introduction

Killing Floor runs on UE2.5, where the server is authoritative and every client holds an approximate
copy of the actors the server decides it needs. Only two things ever cross the wire:

- **Variable replication** - the server pushes changed property values out to clients. One-way,
  server to client, to every client the actor is relevant to.
- **Function replication (RPC)** - one call is executed on the *other* machine instead of this one.
  Either direction, but only between the server and the single client that owns the actor.

Everything else - `Tick`, timers, state code - runs independently on each machine and is expected to
reach the same answer from the same data. That is what `simulated` is for.

**Roles.** `Role` says what *this* machine may do with the actor, `RemoteRole` what the other one
may. The authoritative copy has `Role = ROLE_Authority`; a client's copy is normally
`ROLE_SimulatedProxy`. Only two actors are `ROLE_AutonomousProxy` on their owner's client: its
`PlayerController` and the pawn it possesses. Everything else the client owns - **weapons** and other
inventory - is still a simulated proxy: ownership decides what gets replicated to it (`bNetOwner`),
not the role. See *Client-side roles* below. Every replication condition is written in terms of
these, and the same expression reads differently on each machine. That is what makes
`Role == ROLE_Authority` mean "I am the sender" wherever it appears.

**Relevancy and channels.** An actor is replicated to a client only while the server considers it
relevant to that client, and only through a per-connection *channel* opened for it. No channel means
nothing replicates - no properties, no RPCs. When an actor stops being relevant the channel closes,
and closing a channel normally destroys the client's copy.

**Ownership decides what is possible.**

Function call replication (a.k.a. RPC) is supported *only* between the server and the player who owns the actor (`bNetOwner=true`). Function calls are not replicated to other clients (who have `bNetOwner=false`). A good example is human pawn. You can use RPC between the server and the player who controls the pawn, but those are not replicated to other clients, where you can replicate only properties (and then process them in `PostNetReceive`, `Tick`, `Timer`, etc.).

`PlayerController` exists only on the server and owning player - and that's the only controller the client has.

## Client-side roles: controller, pawn, weapon

On a client in a network game. (On the server, and in a solo game, every actor is
`ROLE_Authority`.)

- **`PlayerController` - `ROLE_AutonomousProxy`.** The client runs non-`simulated` functions on it
  and exchanges RPCs with the server in both directions. A client has exactly one controller - its
  own. The server never sends it anybody else's.
- **Pawn - depends on whose pawn it is.**
  - **The pawn the client controls** (`PlayerController.Pawn`): `ROLE_AutonomousProxy`, with the
    same rules as the controller - non-`simulated` functions run, and RPCs work both ways.
  - **Every other pawn** - other players and all zeds: `ROLE_SimulatedProxy`. Only `simulated`
    functions run. RPCs do not work: the server's `Client*` calls go to that pawn's owner, never to
    this client, and this client's `Server*` calls are thrown away by the server because the client
    does not own the pawn.
- **Weapon - `ROLE_SimulatedProxy`, even for the player holding it.** Only `simulated` functions run
  on the client. RPCs still work, because the player owns the weapon (`bNetOwner=true`) - but with a
  catch the controller and your own pawn do not have: **every `Client*` function on a weapon must be
  declared `simulated`**, and so must everything it calls. A non-`simulated` one is silently dropped
  when the call arrives. That is why stock `Weapon.ClientWeaponSet()` and `KFWeapon.ClientReload()`
  are `simulated`.

  The weapon actor itself - the 1st-person model - is replicated only to its owner, plus anyone
  spectating that pawn; spectators receive it without an `Owner`, so `Pawn.Weapon` stays `none` on
  their machines. Everybody else sees the weapon's `ThirdPersonActor`, the model attached to the pawn.

*ScrN status:* every server-to-client RPC declared by a ScrN weapon or other inventory class is
`simulated`.

# Variable Replication

## Two independent filters

A replicated property reaches a client only if **both** of these pass:

1. **It changed.** The engine remembers, per connection, the last state it sent that client, and
   compares against it. A value equal to what that client already holds is never resent. This is
   automatic and cannot be switched off.
2. **Your condition allows it.** The `reliable if (...)` expression - and it is evaluated **only for
   properties that already failed the first test.**

So a replication condition is *not* a bandwidth filter for unchanged data. It decides **who** gets a
changed value, never **whether** the value changed. Almost everything surprising about `bNetDirty`
follows from that ordering.

## `bNetDirty`

```unrealscript
var transient const bool bNetDirty;  // Actor.uc:182
// "set when any attribute is assigned a value in unrealscript, reset when the actor is replicated"
```

Note **`const`** - script cannot assign it. Nothing in KF or in any ScrN package does.

It is set by the script runtime itself: **assigning any variable that appears in a `replication`
block marks the actor dirty.** Two consequences worth internalising:

- It fires on **assignment, not on change**. `X = X;` dirties the actor. The value filter above
  still stops the redundant send, but the work of comparing every property was already paid for.
- It fires only for variables actually listed in a `replication` block. A property changed by native
  engine code - physics, movement - does not mark the actor dirty. That is exactly what
  `bOnlyDirtyReplication`'s documentation warns about.

### Lifecycle

`bNetDirty` is a single per-actor flag, but replication happens per connection, so there is a
fan-out step most people never see:

1. Script assigns a replicated variable anywhere - the actor is now dirty.
2. **Once per server network tick**, the engine sweeps every actor. Each dirty one marks its channel
   on *every* client connection as needing an update, and the actor's own flag is then cleared.
3. For each connection in turn, `bNetDirty` is **recomputed** to mean "*this* connection has pending
   changes, or this is the initial update", the properties are compared and sent, and the flag is
   cleared again.
4. A lost packet re-marks that one connection, so the update is retried there and nowhere else.

So by the time your replication condition runs, `bNetDirty` is a per-connection value, not the
per-actor one script set.

### What it actually gates

- **The whole property comparison pass.** If a connection has nothing pending and this is not the
  initial update, the engine does not compare that actor's properties at all. This is a **CPU**
  optimisation, not a bandwidth one - the value filter would have suppressed the sends anyway.
- **Groups of rarely-changed `Actor` properties** (`DrawScale`, `DrawType`, the collision flags) are
  only compared when the actor is dirty.
- **`bOnlyDirtyReplication`** - *"if true, only replicate actor if bNetDirty is true - useful if no
  C++ changed attributes (such as physics); only used with bAlwaysRelevant actors"* (`Actor.uc:190`).
  A clean actor is skipped entirely for that connection, before relevancy and priority are even
  considered.

**`Info` sets `bOnlyDirtyReplication=True`** (`Info.uc:59`), so every `ReplicationInfo`, GRI, PRI and
mutator is in this mode by default - `ScrnGameReplicationInfo`, `ScrnCustomPRI` and friends. That is
where dirtiness genuinely decides whether anything happens. (`ScrnBalance` deliberately sets it back
to `False`.)

### In a replication condition it is a tautology

The condition is evaluated **inside** the "is this actor dirty" gate, and only for properties that
already differ. So whenever your condition runs, `bNetDirty` is guaranteed true:

```unrealscript
reliable if ( bNetDirty && Role == ROLE_Authority )        // same as: if ( Role == ROLE_Authority )
reliable if ( (bNetInitial || bNetDirty) && Role == ... )  // same as: if ( Role == ... )
```

The second form is doubly redundant, because `bNetDirty` is computed to include `bNetInitial`. Both
are common in KF's own code and appear in about nineteen places across ScrN. They are harmless and
cost nothing - they simply buy nothing either. No reason to strip them out; good reason not to write
new ones.

### Controlling the update rate instead

What actually decides *when* an actor is considered is `NetUpdateTime` / `NetUpdateFrequency` - an
actor is not looked at until `Level.TimeSeconds` passes `NetUpdateTime`. Hence the working idiom,
already used across ScrN, to push an update out immediately:

```unrealscript
NetUpdateTime = Level.TimeSeconds - 1;
```

## Never write a replicated struct member-wise

Assigning a **member** of a replicated struct does **not** mark the actor dirty. The runtime tracks
the innermost property being written, and a struct's members are not themselves replicated - only
the whole struct variable is.

```unrealscript
MyRepVector = SomeVector;   // marks the actor dirty
MyRepVector.Z = 100;        // does NOT - the change can sit unsent
```

On an `Info`-derived actor (`bOnlyDirtyReplication=True`, see above) that change may never go out at
all until something else dirties the actor. Build the value in a local and assign the whole struct.

Everything else marks dirty as you would expect: plain variables, bools, static array elements, and
dynamic arrays including `.Length`, `Insert()` and `Remove()`. Local variables correctly do not.

*ScrN status:* the eight replicated struct variables - `HopMineProj.RepAttachPos`,
`HunterHellTime.RepTeleport`, `Wraith.RepTeleport`, `ScrnCustomMedicGun.HealLocation` and
`HealRotation`, `ScrnNailGunProjectile.NailHitDelta` and `PendingHitSpot`,
`VagaryClassicProj.RepTargetVel` - are all assigned whole. No member writes anywhere.

## Pawn script properties are throttled to about 11 Hz

A pawn does a *full* update only every 0.09 s for any client that does not own it, and
script-declared replicated properties are skipped entirely on the passes in between.

**Movement is not throttled; state is.** The 0.09 s gate sits after the position code and still
sends `PlayerReplicationInfo` on the way out, so a non-owned pawn keeps replicating on every
considered pass:

- its packed position - `Location`, `Rotation` and `Velocity` together - though only when `Velocity`
  differs from what that client was last sent, plus a forced refresh if more than a second has passed
  while `PHYS_Walking` with the location unchanged;
- `PlayerReplicationInfo`.

Everything else is what gets capped: the remaining native `Actor` / `Pawn` properties, and the whole
script property pass - every variable in your `replication` block.

**The exemption is per connection, not per machine.** The test is `!bTearOff && !bNetOwner`, and
`bNetOwner` is evaluated separately for each connection as that connection's update is built. So on
a dedicated server every client gets the full rate for the one pawn *it* owns and the ~11 Hz cap for
every other pawn - a given pawn is throttled towards everybody except its own player. Torn-off pawns
are exempt too.

**Monsters are never exempt.** No connection owns them, so `bNetOwner` is false everywhere and their
script-replicated state is capped at ~11 Hz for every player, with no exception.

The whole block is wrapped in "not the owner", which has a second consequence: the owning client
never receives the packed position at all. It predicts locally and is corrected through the movement
RPCs instead.

**Server tick rate does not raise the cap.** The 0.09 s is wall-clock, measured per connection
against that connection's last full update, so tick rate only decides how often the pawn is
*considered*. `PossessedBy()` sets `NetUpdateFrequency = 100` and `NetPriority = 3` on every
possessed pawn (`Pawn.uc:747-748`), so on a 100-tick server a pawn is considered almost every tick
and still gets a full update only every 0.09 s:

| | rate on a 100-tick server |
|---|---|
| Packed position (non-owner) | up to ~100 Hz, but only when `Velocity` changes |
| `PlayerReplicationInfo` | every considered pass |
| Native pawn state + **all script-replicated variables** | **~11 Hz** |
| The pawn its owner controls, for that one connection | full rate, every pass |

So raising the tick rate past about 11 buys movement smoothness and RPC latency, and nothing at all
for replicated state on pawns. And ~11 Hz is a *ceiling*, not a promise - relevancy, `NetPriority`
ordering and bandwidth saturation each push it lower, independently per connection. Worth remembering
for anything on `ScrnHumanPawn`.

## Replicating actor destruction

You do not need to replicate it yourself. When the server destroys a replicated actor, the actor
channel closes and the client destroys its own copy, firing `Destroyed()` there. So the hook is:

```unrealscript
simulated function Destroyed()
{
    // client-side effect
    super.Destroyed();
}
```

`simulated` is mandatory - on a simulated proxy a plain `Destroyed()` is swallowed and the actor
just silently vanishes, which is the symptom that makes people invent a `bKillMe` flag.

Three cases where server destruction does **not** reach the client copy:

- **`bNetTemporary=True`** - the client copy is never destroyed by the server. See below.
- **`bTearOff=True`** - the client copy survives and becomes locally authoritative.
- **`bStatic` / `bNoDelete`** - cannot be destroyed during play at all.

**The catch:** `Destroyed()` also fires on the client when the actor merely goes *irrelevant* - the
channel is closed after `RelevantTimeout` (5.0s in the shipped ini) through the identical path. The
client cannot tell "the server killed it" from "it went out of range", and if it becomes relevant
again it is re-created as a fresh actor. If your client-side reaction is a bang or a score tick,
that ambiguity - not the destruction - is the thing worth solving.

### Use `bTearOff`, not a hand-rolled flag

`bTearOff` is the engine's built-in "client, take this over and finish it":

```unrealscript
// server                        // client
bTearOff = true;                 simulated function TornOff()
LifeSpan = 1.0;                  {
                                     // play out the death, then Destroy();
                                 }
```

On receipt the engine sets `Role = ROLE_Authority`, `RemoteRole = ROLE_None`, drops the actor from
the channel, and calls `TornOff()`. Four things follow:

- `bTearOff` is already replicated by `Actor` itself - **no `replication` block of your own**.
- Role is flipped to `ROLE_Authority` *before* `TornOff()` runs, so the client copy is fully
  autonomous afterwards: timers, non-`simulated` functions, state code, its own `Destroy()`.
- `TornOff()` is the one client hook where destroying the actor immediately is unambiguously safe -
  the channel has already released it. Destroying inside `PostNetReceive()` returns into code that
  still touches the actor; it survives as a pending-delete, but it is not clean.
- It is unambiguous: tear-off means "the server is done", never "you walked away".

**Trap:** `bTearOff` replicates under `(!bSkipActorPropertyReplication || bNetInitial)`. If your
actor sets `bSkipActorPropertyReplication=True`, `bTearOff` only ever replicates at spawn - and you
cannot fix that, since a subclass may not re-replicate an inherited property any more than an
inherited function. Those actors need their own flag.

### If you do roll your own flag

- **`reliable` on a variable is a no-op.** The keyword only maps to a *function* flag; a property
  gets the same treatment either way. Required syntactically, meaningless for properties.
- **Use `LifeSpan = 1.0`, not `SetTimer(1.0)`.** `LifeSpan` is not replicated, so it stays
  server-side, it is one line, and it does not consume the actor's single timer slot - if the actor
  already uses `Timer()`, a kill timer silently breaks it.
- The delay is a heuristic, not a guarantee: property updates after the spawn bunch go out
  unreliably, though a nak re-marks them dirty and they are resent while the channel is open and the
  actor relevant. It degrades gracefully - if the flag never lands, the server's `Destroy()` closes
  the channel and the client destroys the actor anyway, just without your effect.

## `bNetTemporary=True`: one bunch, and that is all

For a net-temporary actor the spawn bunch is **also the close bunch**. Consequences:

- The server never sends a second update. **No property change after spawn can ever reach a
  client**, whatever its replication condition says.
- Server `Destroy()` is invisible to clients; the client copy is deliberately *not* destroyed on
  channel close. It is a fire-and-forget simulation that must end itself - its own `Explode()` /
  `HitWall()`, or `LifeSpan` (base `Projectile` ships `LifeSpan=14`).
- `bNetInitial` replication **does** happen - it is the only pass there is. Values are compared
  against the **class defaults**, so only properties differing from their default are sent, which is
  exactly right since the client builds its copy from those same defaults.
- The spawn bunch is sent **unreliably**, so an entire spawn can be lost - the reason a projectile
  occasionally never appears on someone's screen.
- If the bunch **fills up**, the leftovers are dropped with no retry. Only a concern for actors with
  many or large replicated properties.
- **Actor references are the sharp edge.** A reference can only be serialized to a client that
  already has a channel for the target actor. If it does not, the property is skipped and marked for
  a retry - and the retry never comes, because the channel is already closed. The client keeps
  `none` permanently. The engine itself special-cases this for `Instigator`, which it refuses to
  replicate on a temporary actor unless the target is already known to that client.

So on a net-temporary actor, replicate only plain data that is final at spawn, and guard it with
`bNetInitial` to say so.

# Function Replication (RPC)

An RPC is executed *only* on the remote side if such exists, otherwise locally. The "otherwise" part is interesting, as it applies for Solo games (`Level.NetMode == NM_Standalone`) and Listen servers (actors that are owned by the listening players).

Here is a test code from `ScrnPlayerController`:
```
replication
{
    // replicate from client to server
    reliable if ( Role < ROLE_Authority )
        ServerRep;

    // replicate from server to client
    reliable if ( Role == ROLE_Authority )
        ClientRep;
}

function ServerRep(string val)
{
    log("ServerRep << " $ val);
    if (val == "exec") {
        ClientRep("server");
    }
}

function ClientRep(string val)
{
    log("ClientRep << " $ val);
    if (val == "exec") {
        ServerRep("client");
    }
}

exec function TestRep()
{
    log(">>TestRep");
    ServerRep("exec");
    ClientRep("exec");
    log("<<TestRep");
}
```

After entering `TestRep` in console, the exec function calls both server and client function. A string argument is used to avoid recursion and distinguish remote from local calls. Here are the results on different net modes:
```
NM_Standalone:
ScriptLog: >>TestRep
ScriptLog: ServerRep << exec
ScriptLog: ClientRep << server
ScriptLog: ClientRep << exec
ScriptLog: ServerRep << client
ScriptLog: <<TestRep

NM_ListenServer (executed on local PlayerController):
ScriptLog: >>TestRep
ScriptLog: ServerRep << exec
ScriptLog: ClientRep << server
ScriptLog: ClientRep << exec
ScriptLog: ServerRep << client
ScriptLog: <<TestRep

NM_ListenServer (executed on remote client):
ScriptLog: ServerRep << exec
ScriptLog: ServerRep << client


NM_DedicatedServer:
ScriptLog: ServerRep << exec
ScriptLog: ServerRep << client

NM_Client:
ScriptLog: >>TestRep
ScriptLog: ClientRep << exec
ScriptLog: <<TestRep
ScriptLog: ClientRep << server
```

NM_Standalone executes both server and client functions. NM_DedicatedServer executes only server function while NM_Client - only client. NM_ListenServer behaves as NM_Standalone for locally owned actors (local player controller, pawn, etc.) but as NM_DedicatedServer - for remotely owned actors.

## How the engine decides: send or run, never both

A replicated call is **either** sent to the remote machine **or** executed locally - never both, and
occasionally neither. The engine makes that choice at the moment of the call, in this order:

1. **The actor is being destroyed** (`bDeleteMe`) - **runs locally**. A `Client*` call on an actor
   already marked for destruction executes on the server instead of going out.
2. **`Level.NetMode == NM_Standalone`** - **runs locally**, always. The replication condition is not
   even looked at. That is why the solo game above runs both functions, and why a wrong or missing
   `replication` entry is completely invisible offline.
3. **The function is not listed in a `replication` block** - runs locally, *unless* the actor's
   `Role <= ROLE_SimulatedProxy` and the function is not `simulated`, in which case the call is
   swallowed and nothing happens at all. That is the rule the *Simulated* section below describes.
4. **The actor's owning player has no network connection** - **runs locally**. This covers the
   listen-server host (its `Player` is a local viewport, not a network connection) and any
   bot-owned or unowned actor. It is exactly why a listen server behaves like a solo game for
   locally owned actors, and it means a single server-side `ClientFoo()` call site is correct in
   every net mode with no `NM_*` check around it.
5. **The replication condition is evaluated** - as real script, on the calling machine, at the
   moment of the call. **False -> the function runs locally.** True -> it is serialized, sent, and
   the local body is skipped.
6. **An `unreliable` function on a saturated connection is dropped** - neither executed locally nor
   sent. Never put state that must arrive on an `unreliable` function.

Step 5 is the one that catches people out. The condition is not a compile-time annotation; it runs
on every call. So a condition that tests more than `Role`:

```unrealscript
reliable if ( Role == ROLE_Authority && bSomeFlag )
    ClientFoo;
```

quietly executes `ClientFoo()` **on the server** whenever `bSomeFlag` is false, instead of sending
it. Keep replication conditions to the plain `Role` test unless that is genuinely what you want.

## Mirrored conditions are load-bearing

The `Role == ROLE_Authority` / `Role < ROLE_Authority` pair is not decoration - it is what stops an
RPC from bouncing forever. When the call arrives at the far end it is dispatched through the same
machinery, and step 5 runs again there. On the receiving machine the condition is now false
(`Role == ROLE_Authority` does not hold on the client), so the call falls through to local execution
instead of being sent straight back. A condition that evaluated true on both sides would ping-pong
between server and client.

That local execution still obeys the swallowing rule from step 3: if the actor is a simulated proxy
on the receiving machine and the function is not `simulated`, the call is dropped on arrival. It
never bites the controller or the player's own pawn, but it does bite **weapons** - see *Client-side
roles*.

## What the server checks on an incoming RPC

A client-to-server call is validated before it runs. The server re-evaluates the same replication
condition with `Role` and `RemoteRole` swapped - it asks "from where this actor sits on the client,
would this call have been legal?" - and additionally requires `bNetOwner`. If either check fails the
call is discarded and the server logs `Received unwanted function <name> in <actor>` on the
`DevNetTraffic` channel. That channel is suppressed by default; drop the `Suppress=DevNetTraffic`
line from `[Core.System]` in the ini to see it.

Two things follow:

- **This is the engine's only built-in protection against a client calling `Server*` functions on
  actors it does not own.** It says nothing whatsoever about the *arguments*. A client can call any
  `Server*` function on its own controller or pawn with any values it likes, so a `Server*` function
  that trusts its parameters is a cheat waiting to happen - validate them in the body.
- The verdict is cached on the function once it passes, so in practice it runs once per function per
  server session, not once per player or per actor. It is not a per-call permission check.

A server-to-client call is not validated on arrival at all.

## What the function name does and doesn't do

`Client*` and `Server*` are pure convention. The engine never looks at a function's name to decide
anything. The only place a name is used at all is on arrival, to look up the function that came over
the wire; nothing parses the prefix. Direction comes entirely from the replication condition, so you
can call a server-to-client function `ServerFoo` and it will still be sent to the client.

The prefix still earns its place, for one reason: on the calling machine a replicated call silently
does nothing, and the prefix at the call site is the only hint that the body is not running here.
Nothing else about the call says so. **But the prefix can lie and the condition cannot** - when
checking whether a call really crosses the wire, read the `replication` block, not the name, and
remember the block may live several classes up.

### What the compiler does enforce

None of it name-based, all of it worth knowing:

- **One direction per function.** Listing a function under two conditions fails with
  `Function 'X' already has a replication definition`. A function cannot be both directions.
- **Replication must be declared in the class that first declares the function.** Listing an
  override fails with `Function 'X' is defined in base class 'Y'`. So **replication cannot be added
  to an inherited function**: if a stock KF function is not replicated and you need it to be,
  overriding it will not help - give the new function its own name and replicate that. Conversely an
  override inherits the parent's direction and condition automatically, and it is the condition
  declared on the *original* function that gets evaluated, not anything in the subclass.
- **`native final` functions may not be replicated.**
- **A misspelled name in the block is a compile error** - `Bad variable or function 'X' in
  replication definition` - but *omitting* a function is silent: it simply stays a local call. That
  is the mistake the naming convention actually guards against, and only a human reader catches it.
- **Return values are not rejected.** `function bool ServerFoo()` compiles, but on the sending side
  the body never runs, so the caller gets the zero value instead of a result. Never read an RPC's
  return value.

## Consequences

- **A `Server*` function called on the server runs its body immediately**, and a `Client*` function
  called on a client likewise. This is the standard idiom for "apply the effect without a round
  trip": `ScrnPlayerController.PostLogin()` calls `ServerAcknowledgeDamages()` on the server for
  exactly that reason, and `ClientPostLogin()` on the next line for the other direction.
- **Never write code after an RPC call that assumes the body ran.** On the sending side it did not.
- **`ROLE_AutonomousProxy` buys nothing here.** It only exempts the actor from the swallowing rule
  in step 3. It does not let a client run a `Server*` body locally - on the client, a `Server*` call
  is always a send.
- **Solo and listen-server testing hides replication bugs**, because steps 2 and 4 short-circuit
  before the condition is ever evaluated. Test RPC work on a dedicated server
  (run `testRun.cmd /s` from the mod folder).

## Simulated
Note `simulated` keyword is not used for `ClientRep` function. It is because the PlayerController.Role on the client side is `ROLE_AutonomousProxy` - which can execute non-simulated functions. Moreover, marking functions as simulated inside player controller class is useless. "Simulated" has nothing to do with function replication. It only allows function execution when `Role=ROLE_SimulatedProxy`.

### `simulated` is per-function, and `super` does not bypass it

Two rules that follow from the same dispatcher:

- **A `super.` call is not exempt.** Virtual calls, final calls and `super.` calls all reach the
  same check, and it reads the **callee's** flags. So `super.Foo()` from a `simulated` override into
  a non-`simulated` parent is swallowed on a simulated proxy - the parent body simply does not run
  on the client.
- **`simulated` is not inherited.** Only the replication flags propagate from a parent function to
  an override; `simulated` must be written on every implementation that needs it.

`Actor.Destroyed()` is declared `event Destroyed();` - not simulated - so `super.Destroyed()` from a
simulated override *is* absorbed on a simulated proxy. Nothing is lost there, because that body is
empty; it matters the moment a class between yours and `Actor` declares a non-`simulated`
`Destroyed()` with real work in it.

**Still call `super` unconditionally.** It is required on the server and harmlessly absorbed on the
client. What changes is what you may *rely on*: do not assume parent cleanup ran client-side. Where
a parent's client-relevant work is stranded behind a missing `simulated`, copy that body into your
own simulated override - KF will never change underneath you.

Audited for KF projectiles: every `Destroyed()` in every ScrN projectile chain, and in all of their
KF/mod ancestors (`LAWProj`, `M79GrenadeProjectile`, `SealSquealProjectile`, `ShotgunBullet`,
`Nade`, `PipeBombProjectile`, `HuskGunProjectile`, `CrossbowArrow` and the rest), is `simulated`.
The only plain one is the empty `Actor.Destroyed()`, so no ScrN projectile loses parent behavior.
